## Architecture Overview

This spec modifies existing markdown instruction files and one JSON template. No new files are created. The architecture is "edit in place" -- adding sections, instructions, and fields to existing documents.

### Change Categories

1. **state.json template**: Add `phase` field, add `acceptance` object
2. **Skill SKILL.md files**: Add Phase Gate sections, auto-format steps, atomic commit instructions, wiring evidence, pre-acceptance steps
3. **Agent .md files**: Add anti-deferral instructions, types-first enforcement, sweep enforcement, fix budget estimation, doc audit mode

### Phase Ordering Model

```
                    +-----------+
                    |   spec    |  <- /spec sets this
                    +-----------+
                          |
                    +-----------+
                    | validated |  <- /spec-validate sets this
                    +-----------+
                          |
                    +-----------+
                    | executed  |  <- /spec-exec, /spec-loop, /spec-team set this
                    +-----------+
                         / \
            +-----------+   +-----------+
            | accepted  |   |  audited  |  <- either order from "executed"
            +-----------+   +-----------+
                         \ /
                    +-----------+
                    | documented|  <- /spec-docs (requires both accepted + audited? No -- just accepted)
                    +-----------+
                          |
                    +-----------+
                    |  released |  <- /spec-release
                    +-----------+
                          |
                    +-----------+
                    |  verified |  <- /spec-verify
                    +-----------+
                          |
                    +-----------+
                    |   retro   |  <- /spec-retro
                    +-----------+
```

**Phase prerequisite map** (used by phase gate logic):

| Skill | Required phase(s) |
|-------|-------------------|
| /spec-validate | `"spec"` |
| /spec-exec, /spec-loop, /spec-team | `"validated"` |
| /spec-accept | `"executed"` |
| /spec-security-audit | `"executed"` |
| /spec-docs | `"accepted"` |
| /spec-release | `"audited"` or `"accepted"` (security gate in release handles audit) |
| /spec-verify | `"released"` |
| /spec-retro | `"verified"` or `"released"` |

**Design decision**: `/spec-accept` and `/spec-security-audit` both require `"executed"` and can run in either order. The `phase` field advances to whichever ran last. `/spec-docs` requires `"accepted"`. `/spec-release` has its own security gate (existing `findings.critical` check) so it does not strictly require `"audited"` phase -- it requires at least `"accepted"`.

### C-1: state.json Template Changes

- **Purpose**: Add `phase` field and `acceptance` object to the state.json template
- **Covers**: US-1, US-4, US-13, US-14
- **File**: `templates/state.json`
- **Changes**:
  - Add `"phase": null` at top level (after `quick_mode`)
  - Add `"acceptance": { "status": null, "estimated_fix_rounds": null }` at top level (after `security`)
- **Dependencies**: None

### C-2: Phase Gate Section (added to 10 skills)

- **Purpose**: Add a "Phase Gate" section to each pipeline skill that reads state.json.phase and blocks if prerequisite is unmet
- **Covers**: US-1
- **Files**: `skills/spec-validate/SKILL.md`, `skills/spec-exec/SKILL.md`, `skills/spec-loop/SKILL.md`, `skills/spec-team/SKILL.md`, `skills/spec-accept/SKILL.md`, `skills/spec-security-audit/SKILL.md`, `skills/spec-docs/SKILL.md`, `skills/spec-release/SKILL.md`, `skills/spec-verify/SKILL.md`, `skills/spec-retro/SKILL.md`
- **Interface**: Each skill gets a new "## Phase Gate" section inserted after the Usage section and before the Workflow section. The section contains:
  ```markdown
  ## Phase Gate

  Before proceeding, read `state.json.phase`. If the field is absent, treat as `"spec"`.

  **Required phase**: `"<prerequisite>"`

  If `state.json.phase` has not reached `"<prerequisite>"`, display:
  "Phase gate: /spec-<name> requires phase '<prerequisite>' to be complete. Current phase: '<current>'. Run /spec-<prerequisite-command> first."
  Stop execution.

  **Phase ordering** (for reference):
  spec -> validated -> executed -> accepted/audited -> documented -> released -> verified -> retro
  ```
- **Dependencies**: C-1 (phase field must exist in template)

### C-3: Phase Advancement (added to 10 skills)

- **Purpose**: Each skill sets `state.json.phase` to the appropriate value upon successful completion
- **Covers**: US-1
- **Files**: Same 10 skill files as C-2, plus `skills/spec/SKILL.md`
- **Changes**: Add a step at the end of each skill's workflow that updates `state.json.phase`:
  - `/spec` -> `"spec"`
  - `/spec-validate` -> `"validated"`
  - `/spec-exec`, `/spec-loop`, `/spec-team` (on full completion) -> `"executed"`
  - `/spec-accept` (on user acceptance) -> `"accepted"`
  - `/spec-security-audit` -> `"audited"`
  - `/spec-docs` -> `"documented"`
  - `/spec-release` -> `"released"`
  - `/spec-verify` -> `"verified"`
  - `/spec-retro` -> `"retro"`
- **Dependencies**: C-1

### C-4: Dependency Gate Section (added to 3 skills)

- **Purpose**: Add dependency checking logic that verifies dependent specs have reached `"accepted"` phase
- **Covers**: US-2
- **Files**: `skills/spec-exec/SKILL.md`, `skills/spec-loop/SKILL.md`, `skills/spec-team/SKILL.md`
- **Interface**: New "## Dependency Gate" section after Phase Gate:
  ```markdown
  ## Dependency Gate

  Read `requirements.md` for a `## Depends On` section. For each listed dependency:
  1. Read `.claude/specs/<dep-name>/state.json`
  2. Check `state.json.phase` >= `"accepted"` (or if `phase` is absent, treat as not accepted)
  3. If any dependency is not accepted, display:
     "Dependency gate: spec '<dep-name>' is at phase '<phase>', requires 'accepted'. Run /spec-accept <dep-name> first."
     Stop execution.
  ```
- **Dependencies**: C-1 (phase field)

### C-5: Auto-Format Step (added to 3 skills)

- **Purpose**: Run project formatter on changed files after agent merge, before quality gates
- **Covers**: US-3
- **Files**: `skills/spec-exec/SKILL.md`, `skills/spec-loop/SKILL.md`, `skills/spec-team/SKILL.md`
- **Interface**: New "Step 4.7: Auto-Format" section inserted between post-merge regeneration and quality gates:
  ```markdown
  ### Step 4.7: Auto-Format Changed Files

  1. Detect formatter:
     - If `biome.json` exists: `npx biome check --write <changed_files>`
     - Else if `.prettierrc*` exists: `npx prettier --write <changed_files>`
     - Else if `.eslintrc*` exists: `npx eslint --fix <changed_files>`
     - Else: log "No formatter detected, skipping auto-format" to audit log, skip
  2. Filter out `.tsx` and `.jsx` files from `--unsafe` operations
  3. Run the formatter. If it fails, log the error to the audit log and proceed (best-effort).
  4. If changed file list is empty, skip this step.
  ```
- **Dependencies**: None

### C-13: Pre-Acceptance Security Scan (added to spec-accept)

- **Purpose**: Grep for common vulnerability patterns before acceptance
- **Covers**: US-12
- **Files**: `skills/spec-accept/SKILL.md`
- **Changes**: Add "Step 1.6: Pre-Acceptance Security Scan" after the lint step:
  ```markdown
  ### Step 1.6: Pre-Acceptance Security Scan

  1. Read `state.json.reproducibility.git_sha_start`.
  2. If non-null: get changed files via `git diff --name-only <sha>..HEAD`
  3. If null: use all source files (exclude node_modules, dist, .next, vendor, .git)
  4. Grep for patterns:
     - Hardcoded secrets: `password\s*=\s*["']`, `api_key\s*=\s*["']`, `secret\s*=\s*["']`

     - XSS sinks: `dangerouslySetInnerHTML`, `innerHTML\s*=`
     - Insecure crypto: `Math\.random` in security context, `md5(`, `sha1(`
  5. Write results to `evidence/pre-acceptance-security-scan.txt`
  6. Include in acceptor's input. Non-blocking on grep errors.
  ```
- **Dependencies**: None

## Data Models

### state.json Schema Changes

| Field | Type | Default | Description |
|-------|------|---------|-------------|
| `phase` | `string \| null` | `null` | Current pipeline phase. Values: `null`, `"spec"`, `"validated"`, `"executed"`, `"accepted"`, `"audited"`, `"documented"`, `"released"`, `"verified"`, `"retro"` |
| `acceptance.status` | `string \| null` | `null` | Last acceptance result: `"accepted"`, `"not_accepted"`, or `null` |
| `acceptance.estimated_fix_rounds` | `integer \| null` | `null` | Estimated iterations to fix gaps. 0 if accepted. |

### Phase Ordering (for comparison logic)

```
PHASE_ORDER = {
  null: 0,
  "spec": 1,
  "validated": 2,
  "executed": 3,
  "accepted": 4,
  "audited": 4,    // same level as accepted (either order)
  "documented": 5,
  "released": 6,
  "verified": 7,
  "retro": 8
}
```

Phase comparison: `current_phase_order >= required_phase_order`.

Note: `"accepted"` and `"audited"` are at the same level (4). A phase of `"audited"` satisfies the prerequisite for `/spec-docs` (which requires level 4+). Likewise `"accepted"` satisfies `/spec-security-audit` (which requires level 3+).

## Error Handling Strategy

### Error Taxonomy

| Error Class | Source | User-Facing Message | Recovery |
|------------|--------|---------------------|----------|
| Phase Gate Violation | Skill SKILL.md | "Phase gate: /spec-X requires phase 'Y'. Current: 'Z'. Run /spec-Y first." | User runs prerequisite command |
| Dependency Gate Violation | Skill SKILL.md | "Dependency gate: spec 'X' at phase 'Y', requires 'accepted'." | User completes dependency spec |
| Formatter Not Found | Auto-format step | Logged to audit log, execution continues | None needed (best-effort) |
| Formatter Failure | Auto-format step | Logged to audit log, execution continues | None needed (best-effort) |
| Pre-Acceptance Step Failure | Lint/scan/audit | Logged to audit log, acceptance continues | User reviews audit log |
| Fresh Validation Error | Inline validation | Error displayed, debugger dispatched | Auto-fix or manual fix |
| Barrel Reconciliation Conflict | Shared file step | Logged to audit log, debugger dispatched | Auto-fix or manual fix |

### Error Propagation Rules

- **Phase/Dependency gates**: Hard stop. Display message, do not proceed.
- **Auto-format, pre-acceptance steps**: Soft fail. Log to audit log, proceed.
- **Fresh validation**: Attempt auto-fix via debugger. If fix fails, hard stop.
- **Wiring evidence**: Hard gate within execution. Block wave advancement.

## Shared Contracts

### Phase Gate Logic (shared across 10 skills)

The phase gate text block is identical across all skills except for the `required_phase` value. To avoid 10 copies diverging, the design uses a parameterized template:

```markdown
## Phase Gate

Before proceeding, read `state.json.phase`. If the field is absent, treat as `"spec"`.

**Required phase**: `"<REQUIRED_PHASE>"`
**Phase order**: spec(1) -> validated(2) -> executed(3) -> accepted/audited(4) -> documented(5) -> released(6) -> verified(7) -> retro(8)

If `state.json.phase` has not reached the required phase (compare numeric order), display:
"Phase gate: /<SKILL_NAME> requires phase '<REQUIRED_PHASE>' to be complete. Current phase: '<CURRENT>'. Run /<PREREQUISITE_COMMAND> first."
Stop execution. Do not proceed to any subsequent step.
```

Each skill fills in `<REQUIRED_PHASE>`, `<SKILL_NAME>`, and `<PREREQUISITE_COMMAND>`.

## Alternatives Considered

### A1: Centralized Phase Gate Middleware

- **Description**: Create a single "phase-gate.md" file that all skills reference, instead of embedding the gate in each SKILL.md
- **Pros**: Single source of truth, no drift risk
- **Cons**: spec-engine has no import/include mechanism for SKILL.md files -- each skill is self-contained markdown. Adding an include system would be a separate feature.
- **Why rejected**: The plugin architecture does not support cross-file references in skills. Embedding the gate text directly is the only option. The shared contract template minimizes drift by giving taskers identical source text.

### A2: Phase as Derived State

- **Description**: Compute the phase from existing state (file existence, validation.status, task completion, etc.) instead of storing it explicitly
- **Pros**: No new field, no migration concern
- **Cons**: Complex derivation logic would need to be duplicated in every skill. Different skills might derive differently, causing inconsistency. The explicit field is simpler and more reliable.
- **Why rejected**: Explicit `phase` field is deterministic, fast to check, and impossible to miscalculate.

### A3: Pre-Acceptance Steps as Separate Command

- **Description**: Create a `/spec-pre-accept` command that runs lint, security scan, and doc audit, separate from `/spec-accept`
- **Pros**: Clean separation of concerns, can be run independently
- **Cons**: Adds yet another command to the pipeline, increases cognitive load, users would forget to run it
- **Why rejected**: Embedding the steps in `/spec-accept` ensures they always run. The steps are best-effort and non-blocking, so they don't slow down the happy path significantly.

## Migration Plan

- **Database migrations**: None required (no database)
- **Data backfilling**: None required. Existing specs without the `phase` field are handled via backward compatibility (treat as `"spec"`)
- **Backward compatibility**:
  - `state.json.phase`: If absent, all skills treat it as `"spec"`. This means existing in-progress specs can continue -- they just need to run through the pipeline from their current point.
  - `state.json.acceptance`: If absent, ignored. Only populated when /spec-accept runs after this change.
  - All existing skill functionality is preserved. Phase gates and new steps are additive -- they insert new checks before existing workflow steps.
- **Rollback plan**: Revert the 19 modified files to their previous versions via `git revert`. Existing state.json files with the new `phase` field are harmless (unknown fields are ignored by older skill versions).

# Requirements: spec-engine-v3-enforcement

> Generated by spec-engine v2.2.0

## Overview

15 enforcement enhancements for spec-engine based on lessons from 30+ real specs across two production projects. Grouped into 4 priority tiers (P0-P3), these changes harden the pipeline by adding phase gates, dependency checking in skills, auto-formatting, atomic state updates, stronger wiring verification, types-first enforcement, anti-deferral instructions, full-project linting, deprecated field sweep enforcement, fresh pre-execution validation, shared file isolation, security scanning, token budget calculation, fix budget estimation, and documenter audit mode.

All changes target SKILL.md files, agent .md files, and the state.json template. There is no runtime code.

## User Stories

### P0 --- Enforcement Gates

### US-1: Pipeline Phase Gate

**As a** spec-engine user
**I want** each skill to refuse execution if the prerequisite pipeline phase has not completed
**So that** I cannot accidentally run steps out of order (e.g., /spec-docs before /spec-accept)

#### Acceptance Criteria (EARS Notation)

1. WHEN a user invokes any pipeline skill (/spec-validate, /spec-exec, /spec-loop, /spec-team, /spec-accept, /spec-security-audit, /spec-docs, /spec-release, /spec-verify, /spec-retro)
   THE SYSTEM SHALL read `state.json.phase` and verify the prior phase in the ordered sequence `spec -> validate -> exec -> accept -> security-audit -> docs -> release -> verify -> retro` has completed before proceeding

2. WHEN a user invokes a skill whose prerequisite phase is not complete in `state.json.phase`
   THE SYSTEM SHALL display "Phase gate: <skill> requires phase '<prerequisite>' to be complete. Current phase: '<current>'. Run <prerequisite-command> first." and stop execution

3. WHEN `/spec` completes writing requirements.md, design.md, and tasks.md
   THE SYSTEM SHALL set `state.json.phase` to `"spec"`

4. WHEN `/spec-validate` completes with status `"pass"`
   THE SYSTEM SHALL set `state.json.phase` to `"validated"`

5. WHEN `/spec-exec`, `/spec-loop`, or `/spec-team` completes all tasks with status "completed" and wired "yes" or "n/a"
   THE SYSTEM SHALL set `state.json.phase` to `"executed"`

6. WHEN `/spec-accept` receives user acceptance ("Accept this implementation")
   THE SYSTEM SHALL set `state.json.phase` to `"accepted"`

7. WHEN `/spec-security-audit` completes and writes `evidence/security-audit.json`
   THE SYSTEM SHALL set `state.json.phase` to `"audited"`

8. WHEN `/spec-docs` completes generating documentation
   THE SYSTEM SHALL set `state.json.phase` to `"documented"`

9. WHEN `/spec-release` completes generating release.md
   THE SYSTEM SHALL set `state.json.phase` to `"released"`

10. WHEN `/spec-verify` completes all smoke tests
    THE SYSTEM SHALL set `state.json.phase` to `"verified"`

11. WHEN `/spec-retro` completes writing retro.md and lessons.json
    THE SYSTEM SHALL set `state.json.phase` to `"retro"`

12. THE SYSTEM SHALL NOT allow `/spec-exec`, `/spec-loop`, or `/spec-team` to proceed if `state.json.phase` is not at least `"validated"`

13. THE SYSTEM SHALL NOT allow `/spec-accept` to proceed if `state.json.phase` is not at least `"executed"`

14. THE SYSTEM SHALL NOT allow `/spec-docs` to proceed if `state.json.phase` is not at least `"accepted"`

15. [inferred] IF `state.json.phase` field is absent (older spec)
    WHEN a user invokes any pipeline skill
    THE SYSTEM SHALL treat the phase as `"spec"` (backward compatibility) and log "Phase field missing, defaulting to 'spec'" to the audit log

16. [inferred] WHILE `state.json.phase` equals `"executed"`
    THE SYSTEM SHALL allow `/spec-accept` and `/spec-security-audit` to run in either order (both require `"executed"` as prerequisite, not each other)

17. [inferred] WHEN a user invokes `/spec-validate` and `state.json.phase` is absent or `"spec"`
    THE SYSTEM SHALL allow execution (validate's only prerequisite is that spec files exist)

18. [threat-model] THE SYSTEM SHALL NOT expose `state.json` internal field names, absolute filesystem paths, or stack traces in phase gate error messages displayed to the user

### US-2: Spec Dependency Gate in Skills

**As a** spec-engine user
**I want** execution skills (/spec-exec, /spec-loop, /spec-team) to verify cross-spec dependencies before starting
**So that** I cannot begin execution of a spec whose dependencies have not been accepted

#### Acceptance Criteria (EARS Notation)

1. WHEN `/spec-exec`, `/spec-loop`, or `/spec-team` is invoked and `requirements.md` contains a `## Depends On` section with listed dependencies
   THE SYSTEM SHALL read each listed dependency's `state.json.phase`, verify each is at least `"accepted"`, and refuse execution if any is not

2. WHEN a dependency spec's `state.json.phase` is less than `"accepted"`
   THE SYSTEM SHALL display "Dependency gate: spec '<dep-name>' is at phase '<phase>', requires 'accepted'. Run /spec-accept <dep-name> first." and stop execution

3. WHEN a dependency spec directory does not exist
   THE SYSTEM SHALL display "Dependency gate: spec '<dep-name>' not found in .claude/specs/." and stop execution

4. [inferred] WHEN a dependency spec's `state.json` lacks a `phase` field
   THE SYSTEM SHALL treat it as not accepted and display the dependency gate error

5. [inferred] WHEN `requirements.md` has no `## Depends On` section or the section is empty
   THE SYSTEM SHALL skip the dependency check and proceed

6. [threat-model] WHEN constructing the path to a dependency spec's `state.json` in the dependency gate, THE SYSTEM SHALL validate that the spec name contains only alphanumeric characters, hyphens, and underscores, and does not contain path separators or `..` sequences

### US-3: Auto-Format After Every Agent

**As a** spec-engine user
**I want** the orchestrator to automatically run the project's formatter on all files an agent touched, after merge and before quality gates
**So that** formatting failures do not dominate quality gate output

#### Acceptance Criteria (EARS Notation)

1. WHEN an agent completes and its changes are merged (in /spec-exec, /spec-loop, or /spec-team)
   THE SYSTEM SHALL detect the project's formatter from config files (`biome.json` -> `npx biome check --write`, `.prettierrc*` -> `npx prettier --write`, `.eslintrc*` -> `npx eslint --fix`) and run it on the changed files before quality gates

2. WHEN no formatter config file is detected in the project root
   THE SYSTEM SHALL log "No formatter detected, skipping auto-format" to the audit log and proceed to quality gates

3. WHEN the auto-format command fails with a non-zero exit code
   THE SYSTEM SHALL log the failure details to the audit log and proceed to quality gates (formatting is best-effort, not blocking)

4. THE SYSTEM SHALL NOT run the `--unsafe` flag on `.tsx` or `.jsx` files when invoking any formatter

5. [inferred] WHEN the changed file list is empty after merge
   THE SYSTEM SHALL skip the auto-format step

6. [threat-model] WHEN the auto-format step detects a formatter config file, THE SYSTEM SHALL only execute the predefined formatter commands (`npx biome check --write`, `npx prettier --write`, `npx eslint --fix`) and SHALL NOT execute arbitrary commands read from config file contents

### US-4: Atomic state.json Updates Per-Task

**As a** spec-engine user
**I want** state.json to be updated in the same commit as each task's implementation
**So that** the dashboard and status commands always show accurate progress

#### Acceptance Criteria (EARS Notation)

1. WHEN a task is marked completed in /spec-exec, /spec-loop, or /spec-team
   THE SYSTEM SHALL update `state.json.tasks[T-X].status` to `"completed"` and include `state.json` in the same `git commit` as the task's implementation files

2. WHEN a task fails quality gates
   THE SYSTEM SHALL update `state.json.tasks[T-X].failures` and include `state.json` in the rollback or fix commit

3. THE SYSTEM SHALL NOT defer state.json updates to wave boundaries; each task's status change is committed atomically with its code changes

4. WHEN the auto-commit step runs after an agent completes
   THE SYSTEM SHALL include `.claude/specs/<name>/state.json` in the `git add` file list alongside the task's declared Files

### US-5: Grep-Based Wiring Verification Evidence

**As a** spec-engine user
**I want** wiring verification to produce evidence files and serve as a hard gate that blocks wave advancement
**So that** the acceptor has verifiable evidence of wiring and unwired tasks cannot slip through

#### Acceptance Criteria (EARS Notation)

1. WHEN wiring verification completes for a wave in /spec-exec, /spec-loop, or /spec-team
   THE SYSTEM SHALL write `evidence/wiring-wave-N.md` containing: for each task, the export name, grep command executed, grep output (or "no imports found"), and pass/fail determination

2. WHEN any task in the wave has `wired: "pending"` after verification and the task is not marked `wired: "n/a"`
   THE SYSTEM SHALL block wave advancement and log "WIRING HARD GATE: Wave N blocked -- T-X has wired=pending" to the audit log

3. WHEN `/spec-accept` is invoked
   THE SYSTEM SHALL read all `evidence/wiring-wave-*.md` files and include their contents in the acceptor's input

4. WHEN a completed wave lacks a corresponding `evidence/wiring-wave-N.md` file
   THE SYSTEM SHALL flag it as "WIRING EVIDENCE GAP: Wave N has no wiring evidence" in the acceptance report

5. WHEN wiring verification fails (grep finds zero imports) for a task
   THE SYSTEM SHALL include the specific grep command and its empty output in the evidence file for debugging

### US-6: Types-First Wave 0 Enforcement

**As a** spec-engine user
**I want** the validator to check that specs with 5+ tasks have at least one types/schemas task in Wave 0
**So that** parallel agents in later waves cannot disagree on type shapes

#### Acceptance Criteria (EARS Notation)

1. IF a spec has 5 or more tasks
   WHEN the validator runs
   THE SYSTEM SHALL check that Wave 0 contains at least one task whose description or Files field references a types, schemas, interfaces, or shared contracts file

2. IF a spec has 5 or more tasks and Wave 0 contains no types/schemas task
   WHEN the validator runs
   THE SYSTEM SHALL report an ERROR: "Wave 0 has no types/schemas task. Specs with 5+ tasks require contract-first Wave 0."

3. IF a spec has fewer than 5 tasks
   WHEN the validator runs
   THE SYSTEM SHALL skip the types-first Wave 0 check without reporting

4. [inferred] WHEN the tasker generates tasks for a spec with 5+ total tasks
   THE SYSTEM SHALL ensure at least one types/schemas task is placed in Wave 0 (reinforcement of existing contract-first design rule)

### US-7: Remove Deferral Escape Hatches

**As a** spec-engine user
**I want** all agent prompts to contain explicit anti-deferral instructions
**So that** agents implement every acceptance criterion assigned to them without stubs, warnings, or deferrals

#### Acceptance Criteria (EARS Notation)

1. THE SYSTEM SHALL include the following instruction in spec-implementer.md, spec-tester.md, spec-debugger.md, and spec-acceptor.md: "You MUST implement every acceptance criterion assigned to this task. Do not log warnings, add TODO comments, create stubs, or defer to future specs. If you cannot complete a criterion, report it as a failure with specific blockers -- never silently skip it."

2. THE SYSTEM SHALL NOT allow agents to mark a task as completed if their output contains the phrases "deferred to future spec", "TODO: implement later", "stub for now", or "placeholder implementation"

---

### US-8: Full-Project Lint Before Acceptance

**As a** spec-engine user
**I want** a full-project lint to run between final wave completion and /spec-accept
**So that** errors accumulated across waves (not caught by per-wave delta checks) are detected before acceptance

#### Acceptance Criteria (EARS Notation)

1. WHEN `/spec-accept` is invoked
   THE SYSTEM SHALL run the project's lint command (from `state.json.quality_gates.lint_cmd`) on the full codebase before delegating to the acceptor agent

2. WHEN the full-project lint produces errors
   THE SYSTEM SHALL write the lint output to `evidence/pre-acceptance-lint.txt` and include the results in the acceptor's input

3. WHEN the full-project lint produces zero errors
   THE SYSTEM SHALL write "PASS: 0 lint errors" to `evidence/pre-acceptance-lint.txt`

4. WHEN `state.json.quality_gates.lint_cmd` is null or not configured
   THE SYSTEM SHALL skip the full-project lint step and log "Pre-acceptance lint skipped: no lint command configured" to the audit log

5. WHEN the lint command itself fails to execute (not lint errors, but command not found or crash)
   THE SYSTEM SHALL log the error to the audit log, write the error to `evidence/pre-acceptance-lint.txt`, and proceed to acceptance

6. [threat-model] WHEN `state.json.quality_gates.lint_cmd` is used for pre-acceptance lint, THE SYSTEM SHALL validate the command against the `quality_gates.allowed_commands` list before execution; if the list is empty or the command is not in it, log a warning and skip

### US-9: Deprecated Field Sweep Enforcement

**As a** spec-engine user
**I want** the validator to report an ERROR (not just WARNING) if any task has `Deprecates != "none"` but no corresponding sweep task exists
**So that** deprecated field references are always cleaned up

#### Acceptance Criteria (EARS Notation)

1. IF any task in tasks.md has a `Deprecates` field with a value other than `"none"`
   WHEN the validator runs Check 7 (Deprecated Field Detection)
   THE SYSTEM SHALL verify a sweep task exists whose Dependencies include all Deprecates-bearing task IDs

2. IF a Deprecates-bearing task has no corresponding sweep task
   WHEN the validator runs
   THE SYSTEM SHALL report an ERROR: "Task T-X has Deprecates field but no sweep task exists to clean up deprecated references"

3. [inferred] IF a sweep task exists but its Files array does not cover all files with deprecated field references (per grep at validation time)
   WHEN the validator runs
   THE SYSTEM SHALL report an ERROR: "Sweep task T-Y Files array does not cover N file(s) containing deprecated field references"

### US-10: Fresh Pre-Execution Validation

**As a** spec-engine user
**I want** /spec-exec and /spec-loop to run inline validation checks as part of their startup
**So that** execution never starts with a stale or invalid spec

#### Acceptance Criteria (EARS Notation)

1. WHEN `/spec-exec` or `/spec-loop` begins execution (after Step 1.5 drift detection)
   THE SYSTEM SHALL run inline validation: verify task IDs in state.json match tasks.md, wave assignments are consistent, all task dependencies reference valid task IDs, and no circular dependencies exist

2. WHEN inline validation detects an error
   THE SYSTEM SHALL display the error, attempt auto-fix via spec-debugger, and stop execution if the fix fails

3. THE SYSTEM SHALL NOT require a prior `/spec-validate` run to begin execution (the inline validation is sufficient for structural correctness; phase gate requires `"validated"` phase for full EARS/traceability validation)

4. [inferred] WHEN inline validation passes
   THE SYSTEM SHALL log "Fresh validation passed: N tasks, M waves, 0 structural errors" to the audit log

### US-11: Shared File Isolation Enforcement

**As a** spec-engine user
**I want** the orchestrator to enforce that no file from `state.json.parallel.shared_files` appears in parallel tasks' Files arrays within the same wave
**So that** parallel agents cannot cause merge conflicts on shared files

#### Acceptance Criteria (EARS Notation)

1. WHEN `/spec-exec`, `/spec-loop`, or `/spec-team` builds parallel groups for a wave
   THE SYSTEM SHALL check each task's Files array against `state.json.parallel.shared_files` and move any task owning a shared file to a sequential sub-batch

2. WHEN a task is moved to sequential due to shared file ownership
   THE SYSTEM SHALL log "SHARED FILE ISOLATION: T-X moved to sequential -- owns shared file <path>" to the audit log

3. WHEN a parallel wave completes
   THE SYSTEM SHALL run a barrel reconciliation step: for each file in `state.json.parallel.shared_files` that was modified by any task in the wave (detected via `git diff`), consolidate all modifications into a single coherent version

4. [inferred] WHEN barrel reconciliation encounters a conflict that cannot be auto-resolved
   THE SYSTEM SHALL log the conflict to the audit log and dispatch spec-debugger to resolve it

### US-12: Security Scan Per-Spec

**As a** spec-engine user
**I want** a lightweight security grep scan to run before acceptance
**So that** common vulnerability patterns are caught before formal acceptance

#### Acceptance Criteria (EARS Notation)

1. WHEN `/spec-accept` is invoked
   THE SYSTEM SHALL grep all files changed since `state.json.reproducibility.git_sha_start` for common vulnerability patterns: hardcoded secrets (`password\s*=\s*["']`, `api_key\s*=`), SQL injection indicators (`query\s*\+`, template literals in SQL), XSS sinks (`dangerouslySetInnerHTML`, `innerHTML\s*=`), and insecure crypto (`Math.random` used for security, `md5(`, `sha1(`)

2. WHEN the security scan finds matches
   THE SYSTEM SHALL write `evidence/pre-acceptance-security-scan.txt` listing each match with file path, line number, and matched pattern, and include this file in the acceptor's input

3. WHEN the security scan finds zero matches
   THE SYSTEM SHALL write "PASS: No common vulnerability patterns detected" to `evidence/pre-acceptance-security-scan.txt`

4. WHEN `state.json.reproducibility.git_sha_start` is null
   THE SYSTEM SHALL scan all project source files (excluding node_modules, dist, .next, vendor) instead of a diff range

5. WHEN the security scan encounters a grep error
   THE SYSTEM SHALL log the error and continue (the scan is non-blocking)

6. [threat-model] THE SYSTEM SHALL NOT include matched secret values (password strings, API key values) in `evidence/pre-acceptance-security-scan.txt`; only file paths, line numbers, and pattern names shall be written

7. [threat-model] WHEN the pre-acceptance security scan writes evidence, THE SYSTEM SHALL truncate each matched line to 200 characters to limit exposure of surrounding sensitive context

### US-13: Token Budget Auto-Calculation

**As a** spec-engine user
**I want** the token budget to be auto-calculated as `task_count * 50000` tokens
**So that** every spec has a reasonable budget cap without manual configuration

#### Acceptance Criteria (EARS Notation)

1. WHEN `/spec` completes the tasker phase and `state.json.tasks` is populated
   THE SYSTEM SHALL set `state.json.execution.budget_cap` to `task_count * 50000` if `budget_cap` is currently null

2. WHEN `/spec-status` displays budget information
   THE SYSTEM SHALL show the budget source: "Budget: <used>/<cap> tokens (auto-calculated)" if budget was auto-set, or "Budget: <used>/<cap> tokens (manual)" if budget was manually configured

3. THE SYSTEM SHALL NOT overwrite a manually set (non-null) `budget_cap` value

4. [inferred] WHEN the task count changes (tasks added via decomposition during execution)
   THE SYSTEM SHALL NOT recalculate the budget cap (it is set once at spec creation)

### US-14: Post-Acceptance Fix Budget

**As a** spec-engine user
**I want** the acceptor to estimate fix effort for rejected criteria
**So that** I can gauge how much work remains after acceptance review

#### Acceptance Criteria (EARS Notation)

1. WHEN the acceptor produces an acceptance report with overall status "NOT ACCEPTED"
   THE SYSTEM SHALL include an `estimated_fix_rounds` value indicating estimated execution iterations needed (1 = minor wiring fixes, 2-3 = moderate rework, 4+ = significant gaps)

2. WHEN the acceptance report is written
   THE SYSTEM SHALL update `state.json.acceptance.estimated_fix_rounds` with the estimated value

3. [inferred] WHEN the acceptor produces an "ACCEPTED" report
   THE SYSTEM SHALL set `state.json.acceptance.estimated_fix_rounds` to 0

4. WHEN `state.json` does not have an `acceptance` field
   THE SYSTEM SHALL create it with the structure `{ "status": "<accepted|not_accepted>", "estimated_fix_rounds": N }`

### US-15: Documenter as Read-Only Quality Gate

**As a** spec-engine user
**I want** the documenter to run in audit mode before acceptance to check for documentation gaps
**So that** undocumented code is flagged before formal acceptance

#### Acceptance Criteria (EARS Notation)

1. WHEN `/spec-accept` is invoked
   THE SYSTEM SHALL dispatch the spec-documenter agent with read-only audit instructions: "Scan the implementation for documentation gaps. Do NOT generate documentation files. Report: undocumented exports, functions missing JSDoc/docstrings, components missing prop documentation. Write only to evidence/doc-audit.md."

2. WHEN the documenter audit completes
   THE SYSTEM SHALL write `evidence/doc-audit.md` containing: count of undocumented exports, list of functions missing documentation, and an overall documentation coverage estimate as a percentage

3. WHEN the documenter audit identifies gaps
   THE SYSTEM SHALL include `evidence/doc-audit.md` in the acceptor's input as non-blocking context (documentation gaps do not block acceptance)

4. WHEN the documenter audit fails or times out
   THE SYSTEM SHALL log the error to the audit log and proceed to acceptance without the doc audit results

## Non-Functional Requirements

### Performance

1. THE SYSTEM SHALL complete the phase gate check (reading state.json and verifying `phase` field) in under 1 second of wall-clock time for state.json files up to 100KB

2. THE SYSTEM SHALL complete the inline fresh validation check (US-10) in under 5 seconds for specs with up to 30 tasks

### Backward Compatibility

3. THE SYSTEM SHALL treat state.json files lacking the `phase` field as being at phase `"spec"` without producing an error

4. THE SYSTEM SHALL treat state.json files lacking the `acceptance` field as having no acceptance data without producing an error

### Reliability

5. WHEN any newly added pre-acceptance step (full-project lint, security scan, doc audit) fails with an unexpected error
   THE SYSTEM SHALL log the error to the audit log and continue to acceptance (new pre-acceptance steps degrade gracefully)

## Risk Register

| Risk | Likelihood | Impact | Mitigation |
|------|-----------|--------|------------|
| Phase gate blocks /spec-accept on specs created before this change (no `phase` field) | High | High | US-1 AC-15: Treat missing `phase` as `"spec"` with backward-compatible fallback |
| Auto-format introduces code changes that break type checking | Medium | Medium | Format runs before quality gates; debugger handles any resulting failures |
| Atomic state.json commits create merge conflicts in parallel worktrees | Medium | High | state.json updates happen after worktree merge on main branch, not inside worktrees |
| Pre-acceptance steps (lint, scan, audit) significantly slow /spec-accept | Low | Medium | Each step is best-effort and degrades gracefully on failure (NFR-5) |
| Types-first Wave 0 check rejects valid small specs | Low | Low | Only enforced for specs with 5+ tasks (US-6 AC-3) |
| Shared file isolation moves too many tasks to sequential batches | Medium | Medium | Only `shared_files` list triggers isolation; normal file overlap uses existing grouping |
| Anti-deferral instructions cause agents to produce incorrect code rather than reporting blockers | Low | Medium | Instruction explicitly says "report as failure with blockers" as the escape hatch |

## Out of Scope

- Runtime code (JavaScript/Python/Go) -- spec-engine is purely markdown/JSON instruction files
- Changes to shell scripts in `scripts/` or `scripts/lib/` (they wrap skills; changes flow from skills)
- Changes to the plugin.json manifest or version bump
- New slash commands or new agent definitions (this spec modifies existing ones only)
- Changes to preset templates, reference docs, or task-breakdown reference
- Changes to spec-brainstorm, spec-refine, spec-tasks, spec-import, spec-quick, spec-session skills
- Visual/UI changes (there is no UI)

## Security Context

No specific security categories (API endpoints, data storage, external integrations, user input handling) detected. This spec modifies markdown instruction files and a JSON template -- there is no runtime code executing user input or handling network requests. Baseline security criterion applied.

**Baseline criterion** (applied to US-2 as the most externally-facing story):

US-2 AC-6. [security] THE SYSTEM SHALL NOT expose internal error details (stack traces, file paths to the host filesystem, or state.json internal structure) in user-facing phase gate or dependency gate error messages
